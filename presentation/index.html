A detail

How the fascia text is made

  • constants.py — defines the FASCIA_FONT bitmap dictionary and the text string: 
    BRIDGE_FASCIA_TEXT = "LOYOLA UNIVERSITY MARYLAND"
  • geometry.py — general-purpose render_text_flat() and render_text_vertical() functions that walk the bitmap and emit merged brush runs for any flat wall surface.
  • bridge.py — a bridge-specific render_text_fascia() that additionally queries deck_top_z(x) so each letter's Z follows the arch curve. Called twice: once for the south face, and once with text[::-1] and mirror=True for the north face.
  • A set bit in a row means: draw a pixel block there — emitting a small raised Quake brush; consecutive pixels in a row are merged into one box to avoid T-junction sparkling.
  • Word-initial capitals render at full pixel size; other letters shrink by one unit so spacing stays proportional.
  • The north face mirrors each glyph horizontally so the letters read correctly from both sides of the bridge.

The motivation

Why is this?

  • I've long wanted to recreate this map — the campus bridge and dorms I first built in Quake back in the 90s, whose source is long gone.
  • I've been experimenting with map generators since the early days of AI — the idea of describing a world in code and letting a machine help build it.
  • For months the tooling just wasn't good enough — it would fail to build a map that would compile.
  • Only recently has AI become capable enough to actually see it through — and that's what made this map possible.

The workflow

How is this?

  • Mostly prompting — describing features in plain language and letting the AI emit the Python.
  • Shared terminology — a documented naming glossary (e.g. <AREA>_<FEATURE>_<SUFFIX>) gives me & the AI a common vocabulary, so prompts and code refer to the same parts.
  • Reference images in ref/ — real shots of the bridge, hall & dorms guide proportions and detail — alongside screenshots from a Quake map I built in the 90s whose source code is long lost.
  • Google Maps — satellite & Street View to check layout, distances, and the angles the reference photos miss.
  • Quake's viewpos command — print the player's coordinates in-game to capture exact spots for spawns, teleports & props.
  • TrenchBroom round-trips — open loyola.map, eyeball or tweak geometry, then tell the AI to fold changes back into the Python.

Then vs. now

Is this better?

  • Back in the 90s, a level like this meant days, weeks, or months hunched over an editor — placing every brush, vertex, and texture by hand.
  • Lose the source — as I did with my original map — and all that work was simply gone.
  • Now the whole world is described in Python and rebuilt with one command — version-controlled, diffable, and regenerable in seconds.
  • With AI doing much of the work, the bottleneck shifts from labour to ideas.

  • Great for eyeballing geometry, checking spawns, and spotting leaks the compiler would flag.
  • In some cases we've back-ported edits — tweak a brush in TrenchBroom, then fold the change back into the Python so the source stays the single source of truth.
  • Round-trips cleanly: Python → .map  → TrenchBroom → Python.

AI + TrenchBroom

AI helps with TrenchBroom setup too

  • TrenchBroom requires a game configuration — a .cfg file describing entity definitions, WAD paths, and compile tools. The AI wrote and debugged this from scratch.
  • Entity definitions (.fgd) tell TrenchBroom what properties each Quake entity has. The AI generated a working .fgd so spawns and lights display with correct labels.
  • Compile tool paths and custom compile profiles (fast vis, full vis, light) were set up via AI-assisted iteration — no reading through ericw-tools docs by hand.
  • Even the texture browser required pointing TrenchBroom at the right WAD files — the AI knew which settings to change.

The data model

Three dataclasses in quake_loyola.mapdata describe everything:

Face

Three coplanar points define a half-space, plus a texture & alignment.

Brush

An ordered list of faces bounding one convex solid.

Entity

A classname + key/values, optionally with brushes (e.g. func_detail).

MapBuilder collects world brushes & entities, then to_map() serialises the scene.

A key concept

What is a half-space?

  • An infinite plane divides all of 3D space into two halves — everything on one side, and everything on the other.
  • Each Face in a Quake brush defines one such plane (via three coplanar points). The half-space is the region behind that plane (pointing inward).
  • A Brush is the intersection of several half-spaces — "the region that is simultaneously behind all these planes."
  • Because the intersection of half-spaces is always convex, Quake brushes must also be convex — no concave shapes allowed in a single brush.
  • Complex concave geometry is built by combining multiple brushes, each one convex.

Geometry primitives

Shape constructors in quake_loyola.geometry return brushes:

  • box(...) — axis-aligned prism
  • ramp_slab(...) — sloped wedge (X / Y)
  • pyramid(...) — gable roofs & caps
  • arch_seg(...) — one voussoir of an arch
  • arch_wall(...) — a full arched pier
  • layered_wall(...) — multi-storey wall w/ openings

Naming conventions

Constants are defined as <AREA>_<FEATURE>_<SUFFIX> — once you know the vocabulary, names self-describe.

Axis / size

X1/X2 box min/max · CX/CY centre · DZ1/DZ2 deck Z · H/HW height/half-width · T/R/D thickness/radius/depth

Features

PILLAR · BLK · PYR · WIN · ENT · DRIVEWAY_WS/RD/ES (W→E) · KH Knott Hall

Example: BRIDGE_PILLAR_CAP_OVH = bridge pillar cap overhang. Full legend lives in constants.py & the docs.

Understanding the code

  • Procedural at heart — the world is built by functions that emit geometry, not a tree of objects. Each module's build() returns plain (brushes, entities).
  • OOP where it earns its keep — @dataclass Face / Brush / Entity model the .map format; MapBuilder collects & serialises it.
  • Spec dataclasses — BridgeSpec, KnottSpec, DormSpec, LightingPreset bundle related constants into one tidy value.
  • Generators — yield walks floors, arch voussoirs & window rows lazily instead of building big lists.
  • Pure modules — no I/O or globals; geometry in, geometry out, so everything is testable & deterministic.
  • One source of truth — every dimension lives in constants.py, which keeps the math honest.

Quake brushes are inherently data — so a functional, data-first style fits better than deep class hierarchies.

The MapBuilder class

Each area module hands its brushes & entities to one collector; to_map() serialises the whole scene.


class MapBuilder:
    """Accumulates world brushes and entities, then serializes a .map document."""

    def __init__(self):
        self.brushes = []   # worldspawn geometry
        self.entities = []  # point + brush entities

    def add_brushes(self, brushes):  self.brushes.extend(brushes)
    def add_entities(self, entities): self.entities.extend(entities)

    def to_map(self, worldspawn_fields) -> str:
        world = Entity("worldspawn", dict(worldspawn_fields), self.brushes)
        blocks = [world.to_map()] + [e.to_map() for e in self.entities]
        return "\n\n".join(blocks) + "\n"

generate_map.py

The whole entry point — loop every module, collect its geometry, serialise one .map:


MODULES = [streets, west_campus, bridge, knott_terrain, knott_hall, entities]

def build_map():
    """Collect every module's geometry into a MapBuilder."""
    mb = MapBuilder()
    for mod in MODULES:
        brushes, ents = mod.build()
        mb.add_brushes(brushes)
        mb.add_entities(ents)
    return mb

def main():
    mb = build_map()
    with open("loyola.map", "w") as f:
        f.write(mb.to_map(WORLDSPAWN_FIELDS))
    print(f"loyola.map written — {len(mb.brushes)} brushes, {len(mb.entities)} entities")

Room to grow

What could make this better?

AI
  • Automated reference gathering — imagine Claude driving Playwright to browse Google Maps, pull Street View angles & measurements, and feed them straight into the geometry.
Code
  • Static type checking — most geometry functions are still untyped; type hints + mypy (a Vec3 alias, -> list[Brush] returns) would catch argument-order & unit bugs in CI.
Map
  • Realistic trees — the current foliage is crude; proper models or denser func detail would make the campus greenery far more convincing.

Lessons learned

About those robots…

  • Great at the tedious parts — emitting hundreds of brushes, wiring up entities, refactoring a 6,000-line script into a package.
  • Still needs a human in the loop — it guesses wrong, drifts, and happily writes confidently-broken geometry; you have to verify (compile, test, walk the map).
  • You own the code — if you can't read and reason about what it wrote, you can't trust, fix, or extend it.
  • Shared vocabulary & tests are leverage — naming conventions, golden MD5, and CI keep the AI honest.
  • The bottleneck is now ideas — the work shifts from typing to deciding what to build.

Keeping AI honest

The golden hash

  • Every time the map is generated, test_regression.py computes an MD5 of the full .map text and compares it to a known-good value hardcoded in the test.
  • It also checks exact brush and entity counts (currently 822 brushes, 531 entities).
  • If the AI silently changes geometry — misplaces a brush, drops a room, changes a texture — the hash fails immediately in CI before anyone has to open the map in-game.
  • Updating the hash is a deliberate act: you run just update-golden, review the .map diff in version control, and decide whether the change is intentional.
  • It also enforces determinism — a separate test checks that calling the generator twice produces the same output, so there are no hidden random or time-dependent brushes.
